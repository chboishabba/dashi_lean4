# One file: the report, the data and the query engine

```bash
lake build wikidata
./.lake/build/bin/wikidata onepage data/*.wdkb --out site/report.html
```

writes **one** HTML file — [`site/report.html`](../site/report.html), about 3.4 MB,
300 kB over the wire once a host gzips it — that carries everything it needs:

* every ontology of `data/`, verbatim, in the same JSON Lines format `wikidata
  publish` writes;
* the whole diagnostics table, as the CSV `wikidata report` writes;
* a query engine, a chart renderer, an SVG download and a PNG export, in plain
  JavaScript with no dependency;
* the answers of a few queries and the digests of a few charts, computed by the
  verified Lean engine when the file was written, which the page re-computes on
  load and compares against.

There is no server, no build step, no network access and no second file: open it
from a disk, mail it, drop it in a bucket, or commit it to a static host.

## What is on the page

| section | what it does |
|---|---|
| **Query** | pick an ontology, type a query (one atom per line), choose the variables to report, run it; answers download as CSV or JSON |
| **Chart** | five views — the corpus, one ontology, the diagnostics, the answers of the last query, and the `subclass of` neighbourhood of an item — each drawn as SVG |
| **Export** | *Export PNG (2×)*, *PNG (4×)*, *Download SVG*, and *Copy link to this view* |
| **Answers** | the answer table of the last query |
| **The ontologies in this file** | one row per ontology: items, P279, P31, disjointness, validity, content address |
| **Diagnostics** | every issue found, filterable; source, layer, code, severity, status, the items it is about, the message and the suggested fix |
| **Does this browser agree with the verified engine?** | the self check, described below |

The address bar carries the view, the ontology and the query in its fragment, so
*Copy link to this view* produces a link that reproduces the screen — the page
being one file, sharing the file and the link shares the result.

## The query language

The same language, and the same surface syntax, as `wikidata query`:

```
inst ?x Q5          # derived instance of: a P31 statement followed by P279 steps
sub ?x Q35120       # derived subclass of: the reflexive-transitive closure of P279
dinst Q42 ?c        # only what is directly asserted
dsub ?x ?y
class ?x            # metaclass level at least 1
ne ?x ?y
```

A query is a conjunction: one atom per line, all of them must hold. A term is
`?name` for a variable or an identifier such as `Q5` for a fixed item.

## What is proved, and what is only checked

The file is generated by the verified tool, and the *contents* of the file are
covered by theorems:

| about the page | theorem |
|---|---|
| reading an ontology block back out of the page returns exactly the ontology that was published | `Wikidata.OnePage.parseJsonl?_blockPayload_dataBlock` |
| the whole corpus round-trips, sanitising and all | `Wikidata.OnePage.parseDocs?_sanitize_docs` |
| the embedded data cannot close its element or open a tag | `Wikidata.OnePage.scriptSafeB_sanitize`, `Wikidata.OnePage.lt_notMem_sanitize` |
| and that precaution changes nothing in the data actually published | `Wikidata.OnePage.sanitize_eq_self`, `Wikidata.OnePage.scriptSafeB_jsonlOfKB` |
| the diagnostics table reads back exactly as written | `Wikidata.Report.parseCsvText_csvText` |
| the corpus chart has one bar per ontology, and its bars add up to the corpus | `Wikidata.OnePage.corpusBars_length`, `Wikidata.OnePage.corpusBars_count_sum` |
| the chart of one ontology accounts for all of its published rows | `Wikidata.OnePage.kbBars_count_sum` |
| one bar is drawn per entry | `Wikidata.Report.svgBarLines_length` |
| a one-variable query answers with exactly the items that satisfy it | `Wikidata.OnePage.mem_probe_iff`, `Wikidata.Query.mem_eval_iff` |
| the command refuses to write a page whose blocks do not read back | `Wikidata.Cli.kbBlock_roundTrip` (checked again, base by base, at generation time) |

The engine *inside the browser* is JavaScript, so it is checked rather than
proved. The page ships, for every ontology it carries:

* the answers of four one-variable queries, computed by
  `Wikidata.Query.answersT` — the evaluator that `Wikidata.Query.mem_eval_iff`
  characterises;
* the FNV-1a digest (`Wikidata.Publish.fnv1a`) of the corpus chart and of the
  chart of that ontology, as rendered by `Wikidata.Report.svgText`.

On load the page recomputes all of them and shows a badge: for the committed
report that is *121 checks*, and the browser agrees with the verified engine on
all of them — the JavaScript renderer reproduces the verified renderer's drawing
character for character.

## Checking a generated page without a browser

```bash
npm install jsdom
node scripts/verify_onepage.js site/report.html
```

loads the file as a browser would, with no network, and asserts that there is no
script error, that every ontology block was read back, that the self check passes
with no disagreement, that each of the five views draws well-formed SVG, that a
query returns answers, and that the PNG export encodes the drawing losslessly.
Rasterising the drawing is the browser's own step and is left to it.

## Regenerating

```bash
./scripts/make-onepage.sh                  # the whole corpus  -> site/report.html
./scripts/make-onepage.sh data/core.wdkb   # one ontology
OUT=/tmp/small.html ./scripts/make-onepage.sh data/douglas.wdkb
```

The page's stylesheet and script are ordinary files —
[`web/onepage.css`](../web/onepage.css) and [`web/onepage.js`](../web/onepage.js) —
inlined by the command; `--assets DIR` points it elsewhere. Before inlining them
the command checks that neither carries a closing tag of its own kind, and it
refuses to write the page if an ontology cannot be embedded verbatim or if a block
does not read back to the base it came from.
